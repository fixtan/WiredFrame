# デバッグ基盤の使い方（2026-10-12 追加）

複数ウィンドウ（main + サブモニター）でも、問題がすぐ見えるようにするための仕組み。実装は `src/debug.ts`、`src-tauri/src/debug.rs`、`src-tauri/src/monitors.rs`。

## 見る場所

`npx tauri dev` を実行したターミナルに、全ウィンドウのログが集まる。

```
[   12.345s] INFO  [rust] monitors (startup): 6 台
  #0 \\.\DISPLAY1     pos=(0,0) size=2560x1440 scale=1.00 work=2560x1400@(0,0)  [primary]
  ...
[   13.002s] INFO  [sub-monitor-2] boot {...}
[   15.020s] WARN  [sub-monitor-2] 背景画像の読み込みに失敗しました…
```

形式は `[起動からの経過秒] レベル [ウィンドウのラベル] メッセージ`。リリースビルドでは Windows のコンソールがないので、ターミナルには出ない（開発用）。

## 自動で転送されるもの

- 未捕捉エラー、未処理の Promise 拒否
- `console.warn` / `console.error`（同じメッセージは 5 回まで。それ以降は抑制して、その旨を 1 回出す）
- Rust 側の失敗（以前は `let _ =` で捨てていた `set_position` / `show` / `set_fullscreen` など）

意図的にログを出すときは `dlog` / `dwarn` / `derr`（`src/debug.ts`）を使う。

## モニター識別の確認（設計メモの Step 1）

1. 設定でマルチモニターを有効にして、アプリを再起動する（サブウィンドウは起動時にだけ作られる）。
2. トレイの「デバッグ表示」を選ぶ。全モニターに識別用のオーバーレイが出る（ラベル、`idx`、`\\.\DISPLAYn`、位置、サイズ、scale、FPS）。もう一度選ぶと消える。
   - `F2` でも切り替えられるが、フォーカスのあるウィンドウだけ。
3. 同時にターミナルにモニター一覧が出る。Windows の設定アプリの「識別」の番号と見比べる。

起動直後の `current_monitor` はサブウィンドウの位置を移す前の値かもしれない。そのため `boot` と `2s後` の 2 回ログを出している。

## 事実（tao 0.37.1 のソースより）

- Windows の `name` は GDI のデバイス名（`\\.\DISPLAYn`）。
- 列挙順は `EnumDisplayMonitors` の順。設定アプリの番号 1〜6 と一致する保証はない。

## 確認結果（2026-10-12、Windows 実機、6 台）

起動時のモニター一覧（ターミナルのログ）:

| idx | name | pos | size | 設定アプリの番号（配置図から推定） |
|---|---|---|---|---|
| 0 | `\\.\DISPLAY1` | (0,0) | 3840x1600 | 1（primary） |
| 1 | `\\.\DISPLAY2` | (3840,1) | 1200x1600（縦画面） | 2 |
| 2 | `\\.\DISPLAY3` | (-1920,0) | 1920x1080 | 3 |
| 3 | `\\.\DISPLAY4` | (0,1600) | 1920x1080 | 4 |
| 4 | `\\.\DISPLAY12` | (-3840,0) | 1920x1080 | 5 |
| 5 | `\\.\DISPLAY13` | (1920,1600) | 1920x1080 | 6 |

事実（ログとスクリーンショットから）:

- 6 ウィンドウすべてが、自分のモニターと一致する情報を出した。`available_monitors` と不一致の警告は出ていない。FPS は全ウィンドウで 60。
- `boot` と `2s後` のモニター情報は全ウィンドウで同じだった。起動直後の `current_monitor` は、この環境ではそのまま使えた。
- `name` は DISPLAY1, 2, 3, 4, **12, 13**。連番ではないので、設定アプリの番号とは別物。
- 列挙順の idx + 1 は、設定アプリの配置図の番号と 6 台すべてで一致した（位置関係から推定。設定アプリの「識別」ボタンでは確認していない）。
- 起動直後の viewport は、モニターの高さより 30px 大きいことがある（1920x1110、1200x1630）。4 回の起動・延べ 20 ウィンドウのうち 10 で起き、どのウィンドウで起きるかは毎回違う（Rust がサイズ設定とフルスクリーン化をするタイミングとの競合と思われる。原因は未調査）。フルスクリーン化後は、オーバーレイの viewport / canvas ともにモニターと同じサイズになっていた。
- `setTimeout(2000)` が、起動ログの 2.0〜5.4 秒後に発火した（`2s後` のログの時刻）。原因は未調査（非アクティブなウィンドウのタイマー制限か、テクスチャ読み込みで忙しいか）。FPS（`requestAnimationFrame`）は 60 のまま。
- 縦画面（idx 1、1200x1600）では、10 列 × 6 行のグリッドが収まらない。右側が見切れ、左端のタイルも切れている。`cols` / `rows` の可変化とカメラのフィットが必要（設計メモ 3.3）。
- `THREE.Clock` の非推奨警告が全ウィンドウで出ている（`AppManager.ts` の Clock）。警告のみで動作には影響していない。今回のログ転送で初めて見えた。

示唆（Claude の意見）:

- 起動時の `innerWidth` / `innerHeight` を使う計算（グリッドのフィットなど）は、フルスクリーン化後の `resize` を待ってからにする。
- 時間に敏感な処理（回転の切替など）は、`setTimeout` ではなく `requestAnimationFrame` の経過時間（今の `TileMode.update(delta)` の方式）で動かす。サブウィンドウの `setTimeout` は遅れることがある。

## 再起動・ケーブル抜き差しの確認（2026-10-12、3 回の起動）

順番: ① PC を落として再起動 → ② モニター 1 台のケーブルを抜いて起動 → ③ 繋ぎ直して起動。

- 3 回とも、`name`・idx・位置・サイズが完全に同じ 6 台のリストだった（DISPLAY1, 2, 3, 4, 12, 13）。
- ② ではケーブルを 1 台抜いていたのに、リストは 6 台のままだった。どのモニターを抜いたかは記録していない。Windows が切断後もそのモニターを列挙し続けた可能性があるが、未確認。
- つまり、この 3 パターンでは `name` と idx は変わらなかった。変わるケース（別のポートに挿し替える、配置を変えるなど）は確認していない。
- Windows のマルチモニターは昔から不安定で、番号が変わったり、ケーブルを挿し直すと設定が変わったりすることがある（ユーザーの経験）。このアプリでも同じことが起きる前提で、おかしくなったら設定し直す運用にする。
- 設定の保存キーは `name + 解像度`（例 `\\.\DISPLAY12|1920x1080`）に決めた。経緯は `multi-monitor-design.md` の 3.1 を参照。

## Step 2（設定の保存）の確認で見るログ

ターミナルに、ウィンドウごとにこの形で出る。

```
[   1.9s] INFO  [sub-monitor-2] 設定: モニターキー = \\.\DISPLAY3|1920x1080
[   2.0s] INFO  [sub-monitor-2] 設定: 読込 (boot) key=\\.\DISPLAY3|1920x1080 source=default {...}
```

- 初回の起動で旧設定がある場合は、`設定: v1 → v2 に移行した` が 1 回出る。
- `source=` は、どの保存値を使ったか（`monitor` = そのモニター専用 / `default` = 共通の既定値 / `builtin` = 組み込みの初期値）。
- main で保存すると、全ウィンドウに `設定: 読込 (settings-changed)` が出る。ウィンドウ間で `{...}` の中身が違えば、保存値が共有されていない。
- 保存値が壊れていたり、型・値が不正なときは、`WARN 設定: …` で項目名つきで出る。

### 実機での確認結果（2026-10-12、6 台）

- v1 → v2 の移行ログは 1 回だけ。各ウィンドウが自分のモニターキーを解決し、`source=default` で読み込んだ。
- 全 6 ウィンドウの `{...}` の中身が同一 → `localStorage` は共有されている。
- main で保存（playMode を fixed → rotation）すると、全 6 ウィンドウに `設定: 読込 (settings-changed)` が出て、約 2ms 以内に適用された。
